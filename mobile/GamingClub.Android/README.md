# GamingClub.Android — вариант 18

Android Studio / Kotlin, ветка `feature/android-client`, draft PR №1. **Исходный код без проверки сборкой**.

## Шесть разделов интерфейса

1. **Вход** — вход существующего пользователя и регистрация нового посетителя.
2. **Зал** — схема по координатам SQL, выбор компьютера.
3. **Бронирование** — выбор тарифа и UTC-интервала, отправка на API.
4. **Мои брони** — загрузка бронирований владельца по JWT; отмена будущей активной брони с подтверждением.
5. **Сессия** — запуск, таймер с обновлением каждые 5 секунд, продление на 30 минут.
6. **Профиль** — отображение логина и роли, выход.

Технически сейчас это шесть переключаемых разделов одной Activity, а не шесть отдельных Activity/Fragment. Для отчёта по практике можно подготовить шесть снимков экранов **после проверки сборкой**. Макеты Figma ещё не готовы.

## Запуск на эмуляторе

1. В SQL Server развернуть `database/schema.sql` и `database/seed.sql`.
2. Если БД создана по старой версии схемы, применить `database/migrations/001_void_pending_payments.sql` через SSMS.
3. В PowerShell настроить `ConnectionStrings__GamingClub` и `GAMINGCLUB_JWT_SECRET` по `docs/auth-verification.md`.
4. Установить `ASPNETCORE_ENVIRONMENT=Development`, запустить API на `http://localhost:5080`. Сохранять такой API только на компьютере для отладки.
5. В Android Studio открыть `mobile/GamingClub.Android`; установить Android SDK 35 и JDK 17.
6. Запустить Debug-сборку в эмуляторе. `10.0.2.2` — адрес компьютера с API с точки зрения эмулятора.
7. На экране «Вход» зарегистрировать пользователя: имя, логин (ASCII 3–80 символов), пароль от 12 символов.
9. Открыть «Зал», выбрать активный ПК, затем «Бронирование», выбрать тариф и будущий UTC-интервал (целые минуты).
8. Открыть «Мои брони», проверить, что отображается только собственная бронь. Выбрать будущую ACTIVE-бронь и проверить отмену (статус `CANCELLED`, счёт `VOID`).
10. Запуск сессии возможен только после наступления начала брони. Затем открыть «Сессия», проверить таймер и продление.
11. В «Профиль» выйти из учётной записи. Токен хранится только в памяти приложения.

## Особенности и ограничения

- Debug-версия использует HTTP только для эмулятора; release не имеет рабочего серверного адреса.
- Приложение не передаёт чужой пользовательский ID как удостоверение личности: сервер берёт ID из JWT.
- Цвет схемы показывает только `IsActive`, но не резервирование на заданное время. Финальное подтверждение делает сервер.
- После перезапуска Activity вход не сохраняется. При выходе токен очищается из оперативной памяти.
- Это учебный прототип: нет защищённого постоянного хранения токена, выбора локального часового пояса, оплаты, Figma, реального APK или выполненных проверок.
- Для безопасного production необходимо HTTPS, доработка авторизации, rate limiting, интеграционные и UI-тесты.


Для защиты подготовлены макеты шести разделов: `docs/design/screens.md` и SVG в `docs/design/` (они находятся в основной ветке). Это макеты для Figma, не снимки реально собранного APK.
