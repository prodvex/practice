# Отмена бронирования — функциональные правила и проверка

**Статус:** исходники добавлены в GitHub, реальная сборка и проверки НЕ проводились.

## Перед запуском

Для **новой базы** достаточно актуального `database/schema.sql`. Если база GamingClub или GamingClubTest_18 уже создавалась по старой схеме, **обязательно выполнить** `database/migrations/001_void_pending_payments.sql` через SSMS с выбором правильной базы. Миграция допускает только эти два имени, выполняется в SQL-транзакции и откатывает изменение ограничения при ошибке.

## Правила

1. Посетитель вызывает `POST /api/bookings/{id}/cancel` с JWT и может отменить только **свою** бронь; чужая возвращает HTTP 404.
2. Администратор вызывает `POST /api/admin/bookings/{id}/cancel` с ролью ADMIN.
3. Статус брони должен быть `ACTIVE`, а начало `StartUtc` — позже текущего времени сервера.
4. У брони не должно быть ни одной строки `Sessions`: начатую сессию нельзя отменить.
5. Оплаченная или ранее возвращённая оплата требует отдельного финансового процесса. Такой запрос отмены возвращает HTTP 409.
6. Неоплаченные `Payments(PENDING)` переходят в `VOID` — **это аннулирование начисления, не возврат денег**.
7. `Bookings.Status` меняется на `CANCELLED` в той же SQL-транзакции. Освобождённое время можно забронировать снова.

## Swagger

Предусловия: запустить API по `docs/local-setup.md`, зарегистрировать посетителя, получить токен через `POST /api/auth/login`, создать будущую бронь и сохранить `bookingId`. Передать заголовок `Authorization: Bearer <token>`.

```http
POST /api/bookings/123/cancel
Authorization: Bearer <token>
```

Ожидаемое успешное тело: `error: 0`, `voidedInvoices: 1` (для одной PENDING-записи). Тело конкретного ответа проверить по Swagger, а не считать заранее измеренным результатом.

## Ручные тесты

| ID | Сценарий | Ожидается |
|---|---|---|
| CN-01 | Отмена собственной будущей ACTIVE-брони | HTTP 200; CANCELLED и VOID |
| CN-02 | Повторная отмена | HTTP 409 |
| CN-03 | Бронь другого пользователя | HTTP 404 |
| CN-04 | Нет токена | HTTP 401 |
| CN-05 | VISITOR вызывает /api/admin/.../cancel | HTTP 403 |
| CN-06 | Оплаченный счёт PAID | HTTP 409 без изменения данных |
| CN-07 | Сессия уже запущена | HTTP 409 |
| CN-08 | Бронь уже началась | HTTP 409 |
| CN-09 | После отмены повторно занять тот же интервал | Бронирование возможно |
| CN-10 | Параллельная отмена и бронирование | Не более одного конфликтующего ACTIVE-интервала |

SQL-проверка:

```sql
USE GamingClub;
SELECT BookingId, Status, StartUtc, EndUtc FROM dbo.Bookings ORDER BY BookingId DESC;
SELECT BookingId, AmountRub, PaymentStatus FROM dbo.Payments ORDER BY PaymentId DESC;
```

**Ограничения:** нет рабочего платёжного шлюза, штрафов за отмену, процедур возврата оплаченной брони и отдельного журнала аудита. До реального запуска все результаты тестов считаются неизвестными.
