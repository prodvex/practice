# SQL-интеграционные тесты GamingClub — вариант 18

## Изолированная база

В репозитории есть `database/schema-integration-tests.sql`. Это отдельная копия учебной схемы, создающая **только** базу `GamingClubTest_18` (не `GamingClub`). Не запускайте её на боевом сервере. Для создания тестовой БД нужны соответствующие права; повторно запускать скрипт на уже созданных таблицах нельзя.

1. Откройте `database/schema-integration-tests.sql` в SSMS на локальном SQL Server Express/Developer.
2. Выполните скрипт **один раз**. Он создаст базу и таблицы; загружать `database/seed.sql` не нужно.
3. В той же сессии PowerShell, откуда будете запускать тесты, установите:
   ```powershell
   $env:GAMINGCLUB_TEST_SQL_CONNECTION = "Server=localhost\SQLEXPRESS;Database=GamingClubTest_18;Trusted_Connection=True;TrustServerCertificate=True"
   ```
4. Команда запуска:
   ```powershell
   dotnet test tests/GamingClub.Tests/GamingClub.Tests.csproj --filter "FullyQualifiedName~SqlBookingIntegrationTests|FullyQualifiedName~SqlAdminIntegrationTests" --logger "console;verbosity=normal"
   ```

**Защита данных:** при отсутствии `GAMINGCLUB_TEST_SQL_CONNECTION` атрибут `[SqlServerFact]` помечает тесты как *Skipped*, не как *Passed*. При неправильном имени базы выполнение прерывается исключением. Ни один тест не удаляет чужую базу. Тесты оставляют синтетические записи с уникальными идентификаторами — перед повторными запусками можно создать новую чистую тестовую БД в отдельной локальной среде; автоматическая очистка пока отсутствует.

При обновлении уже созданной `GamingClubTest_18` с прежним ограничением платежей запустите миграцию `database/migrations/001_void_pending_payments.sql`, выбрав тестовую БД в SSMS.

## Сценарии

| ID | Операция | Ожидаемый результат |
|---|---|---|
| SQL-01 | Создать бронь | В `Bookings` одна запись, в `Payments` сумма с `PENDING` |
| SQL-02 | Пересекающаяся бронь | Конфликт, вторую запись создать нельзя |
| SQL-03 | Соседние интервалы | Обе брони создаются |
| SQL-04 | Два клиента одновременно | Только один создаёт бронь, второй получает конфликт |
| SQL-05 | Отключённый ПК | Бронирование отклонено |
| SQL-06 | Продление при будущей брони | Конфликт; старое время и количество оплат не меняются |
| SQL-07 | Успешное продление на 30 минут | Время обновлено, дополнительная оплата `PENDING` |
| SQL-08 | Создание и архивирование тарифа | Запись остаётся в БД, `IsActive=0` |
| SQL-09 | Ночной тариф 22:00–06:00 | Окно времени сохраняется |
| SQL-10 | Повтор названия тарифа | Ошибка уникальности |
| SQL-11 | Отмена будущей брони | `CANCELLED`, начисление `VOID`, место можно снова забронировать |
| SQL-12 | Повторная отмена | Конфликт, без нового начисления |
| SQL-13 | Оплаченная бронь | Отказ в простой отмене; `PAID` не становится `REFUNDED` |

Ещё один обычный unit-тест проверяет отклонение некорректного тарифа до обращения к БД.

## Ограничения

- Это интеграция с живым SQL Server на уровне классов хранилища, а не Android→HTTP→SQL Server end-to-end.
- HTTP-тесты авторизации находятся в `ApiAuthorizationIntegrationTests.cs`; они работают без SQL.
- Нужны фактические результаты запуска, протокол тестирования, скриншоты, отчёт покрытия, SQL-запросы для проверки данных.
- Прототип имеет открытые `/api/dev/*` маршруты в режиме Development — сервер должен работать исключительно локально.
- Для исторически корректного расчёта ночного тарифа и готовой финансовой отчётности нужны дополнительные правила часового пояса/изменения ставок.

Не указывайте `PASS` в отчёте, пока тест не был реально запущен.
