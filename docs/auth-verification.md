# GamingClub: регистрация, JWT и права доступа

**Статус:** исходный код добавлен, сборка и запуск пока не выполнялись. В Production использовать HTTPS, ограничение частоты запросов, аудит, централизованное управление секретами и проверенное хранилище данных.

## Как настроить

1. Выполнить `database/schema.sql`, затем `database/seed.sql`. Таблицы `Roles` и `Users` уже созданы.
2. Создать случайный секрет не короче 32 байт. Для локального PowerShell:
   ```powershell
   $bytes = New-Object byte[] 48
   [Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
   $env:GAMINGCLUB_JWT_SECRET = [Convert]::ToBase64String($bytes)
   $env:ASPNETCORE_ENVIRONMENT = "Development"
   ```
   Не публиковать значение в Git, отчётах или скриншотах.
3. Установить `ConnectionStrings__GamingClub` по `docs/local-setup.md`.
4. Запустить сервер локально: `dotnet run --project src/GamingClub.API --urls http://localhost:5080`.

## REST endpoints

| Маршрут | Кто может вызывать |
|---|---|
| POST /api/auth/register | Все, создаёт только VISITOR |
| POST /api/auth/login | Все, с логином и паролем |
| GET /api/me | Авторизованный пользователь |
| GET /api/bookings/mine | Авторизованный пользователь, только свои |
| POST /api/bookings | Авторизованный, UserId из токена |
| GET /api/sessions/{id} | Владелец брони или ADMIN |
| POST /api/sessions/{id}/start | Владелец брони или ADMIN |
| POST /api/sessions/{id}/extend | Владелец брони или ADMIN |
| GET /api/admin/reports/occupancy | Только ADMIN |

Роль `ADMIN` не выдаётся при саморегистрации. Назначать её должен уполномоченный администратор через защищённую процедуру, которую ещё необходимо реализовать. Для учебного испытания роль можно назначить вручную в локальной БД после проверки пользователя, но не выполнять такую операцию в открытом API.

## Проверка

```json
POST /api/auth/register
{"login":"visitor18","password":"UseUniqueLongPassword_18","displayName":"Тестовый посетитель"}
```

После регистрации сервер должен вернуть `accessToken`, `userId`, `role=VISITOR`. Для следующих запросов добавьте заголовок `Authorization: Bearer <accessToken>`. Время действия — 2 часа, постоянное хранение токенов на Android не реализовано.

1. Повторная регистрация того же логина → ошибка 400.
2. Неверный пароль → 401.
3. Запрос `/api/me` без токена → 401.
4. После успешного входа `/api/me` возвращает ID, логин, роль.
5. `/api/bookings/mine` возвращает только брони владельца.
6. Параметр `userId` при создании брони игнорируется: сервер подставляет ID из JWT.
7. Прочитать или продлить чужую сессию посетителю нельзя.
8. Запрос `/api/admin/reports/occupancy` от VISITOR → 403.

## Ограничения безопасности

- `/api/dev/*` **не требуют JWT**. Они регистрируются только в Development и предназначены исключительно для локального эксперимента; не выставлять Development API в Интернет.
- HTTP на Android разрешён только debug-сборке для эмулятора. Реальные устройства и публикация требуют HTTPS.
- Нет подтверждения email, восстановления пароля, блокировки перебора, ограничения частоты запросов, refresh token и отзыва токенов.
- Пароли хешируются PBKDF2-SHA256 с солью. Тестовый пользователь `demo_241810` из seed не имеет пригодного пароля; он не может входить через обычную авторизацию.
- Нет реального механизма назначения администраторов (пока только существующая роль в SQL).
- Без результатов реального запуска нельзя утверждать, что маршруты и права доступа проверены.
